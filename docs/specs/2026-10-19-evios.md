Передача доступа работодателю — отдельное действие по указанию пользователя.

## Текущее состояние

Исходная точка — Full Stack FastAPI Template, коммит `b1125d8839482cb7bbae603ddc6d0081bf87532e`; происхождение записано в [upstream.md](../upstream.md). В исходном коде права определялись булевым `User.is_superuser`: администратор управлял пользователями, обычный пользователь работал со своим профилем и своими объектами `Item`. Роли менеджера и страницы метрик не было. При прямом открытии `/admin` обычный пользователь перенаправлялся на главную без объяснения.

Backend использует FastAPI, SQLModel, PostgreSQL, Alembic и JWT. Frontend использует React, TypeScript, TanStack Router/Query и клиент, генерируемый из OpenAPI. В шаблоне есть отдельные схемы административного обновления пользователя и изменения собственного профиля — это разделение сохранить.

В текущей рабочей версии уже добавлены роли, зависимости проверки разрешений, метрики, миграция и интерфейс отказа в доступе. Локальная проверка ведётся на отдельных портах: PostgreSQL `55433`, API `8001`, frontend `5174`; адрес — `127.0.0.1`. Существующие сервисы на других портах не использовать как тестовую базу.

## Ограничения и границы

- Работать в существующем стеке. Не заменять шаблон и не добавлять внешнюю систему политик, отдельный сервис авторизации или динамический редактор ролей.
- Работодатель предлагает ориентироваться на один час. При сокращении объёма первыми исключаются необязательные ADR, диаграммы и дополнительные функции; проверки API, миграция и инструкции запуска обязательны. Не выдавать оценку времени за фактическое измерение.
- PostgreSQL хранит единственную каноническую роль пользователя. Поле `is_superuser` удалить после переноса данных; не оставлять параллельный флаг, alias или совместимость с прежним API.
- В JWT не записывать права. Читать актуальную роль и активность из базы при каждом запросе. Уже выданный токен не должен сохранять отозванные права.
- Разрешения, возвращаемые API, — производные от роли. Frontend использует их для отображения, но не является границей безопасности.
- В шаблоне нет глобальных настроек продукта. Не придумывать CRUD настроек ради формулировки задания. Личные настройки доступны всем ролям; административные действия — только администратору.
- Сохранить авторизацию, смену пароля и работу с собственными `Item`. Сохранить существующий административный доступ к чужим `Item`; менеджеру его не давать.
- Удалить открытый служебный endpoint создания пользователей из режима разработки. Тестовые аккаунты создавать через seed или обычную регистрацию. Удалённый URL должен возвращать 404 без `Location`; не заменять его редиректом или страницей приложения.
- Не добавлять декоративные надзаголовки, микрометки или ссылки над заголовками. Навигация остаётся в боковой панели и действиях страницы.
- Не коммитить `.env`, настоящие токены, JWT, состояние авторизованного браузера, локальную базу или внутренние инструкции AI. Пример конфигурации содержит только явно обозначенные локальные демонстрационные значения.
- Backend-тесты очищают пользователей и `Item` после выполнения. Запускать их только на отдельной одноразовой базе.
- Метрики ограничены текущим количеством пользователей и объектов. SMTP и полноценная система аналитики не входят в критерии этого задания.

## Модели и данные

### Канонические данные

`User.role` — обязательное поле со значениями `admin`, `manager`, `member`; значение нового пользователя — `member`. В Python используется `StrEnum`, в PostgreSQL — VARCHAR с ограничением CHECK. Проверка должна работать и через Pydantic, и на уровне базы.

`UserCreate` и `UserUpdate` принимают роль только в административных обработчиках. Неизвестная роль, явный `null` для роли/активности и устаревший `is_superuser` отклоняются с 422. `UserRegister` и `UserUpdateMe` не принимают роль, активность или готовый список разрешений; лишние поля отклоняются, а не молча игнорируются.

### Производные данные

`UserPublic.permissions` вычисляется из `role` на сервере. Отдельную колонку, JSON или таблицу для списка разрешений не создавать. `/users/me` возвращает актуальные `role` и `permissions`; хеш пароля в ответ не попадает.

`MetricsPublic` содержит `users: int` и `items: int`. Значения вычисляются запросами COUNT при обращении; фоновые задачи, периодический пересчёт и опрос состояния задач не нужны.

### Миграция

1. Добавить `role` с временным значением по умолчанию `member`, чтобы заполнить существующие строки.
2. Перевести `is_superuser=true` в `admin`, остальные строки оставить `member`.
3. Добавить CHECK на три допустимых значения.
4. Удалить `is_superuser` и временный серверный default. Значение нового пользователя задаёт модель.
5. При downgrade восстановить boolean: `admin → true`, `manager/member → false`. Отличие менеджера от участника при откате теряется; это явно указать в README.

Не запускать миграцию на посторонних или рабочих базах. Перед применением к существующим ценным данным нужна отдельная резервная копия; текущее задание проверяется на изолированных локальных базах.

## План реализации

### 1. Зафиксировать исходную точку

Сохранить SHA и MIT-лицензию шаблона, сделать отдельный исходный коммит. Установить зависимости из lock-файлов, поднять отдельную PostgreSQL, применить исходные миграции и запустить неизменённые CRUD-тесты. Открыть исходный интерфейс в браузере и сохранить доказательство запуска.

Контрольная точка: исходный шаблон запускается; последующие изменения можно сравнить с отдельным baseline-коммитом; посторонние сервисы не затронуты.

### 2. Ввести роль и перенести данные

Добавить enum, поле, ограничения и Alembic-миграцию. Обновить создание первого администратора. На отдельной базе подготовить две старые записи с разными значениями boolean и проверить upgrade, запрет неизвестной роли и downgrade.

Контрольная точка: старый администратор остаётся администратором; обычный пользователь получает member; в актуальной таблице нет `is_superuser`.

### 3. Защитить обработчики API

Создать небольшую фабрику FastAPI-зависимостей. Для списка пользователей требовать `users:read`, для создания/изменения/удаления — `users:write`, для метрик — `metrics:read`. Во всех случаях сначала аутентифицировать пользователя и проверить `is_active`.

Собственный профиль обрабатывается отдельной входной схемой. Не принимать административные поля ни на `/users/me`, ни на `/users/signup`. Удалить служебное создание пользователей; сохранить явный 404 неизвестных API URL даже при включённой раздаче frontend.

Контрольная точка: прямой HTTP-запрос с подменённым клиентом не обходит права; запрет не изменяет данные; изменение роли в БД влияет на существующий JWT.

### 4. Передать разрешения и обновить интерфейс

Добавить вычисляемый список разрешений в `UserPublic`, затем выполнить `make client`. Настроить `can()` на основе типизированного списка. Скрыть недоступные пункты и действия; менеджеру оставить чтение пользователей. Добавить Metrics и общий Access denied. Не подменять отказ молчаливым редиректом.

Очищать клиентский cache при смене аккаунта. Проверка текущих разрешений выполняется при входе в защищённый маршрут; данные текущего пользователя также обновляются через TanStack Query. Постоянный опрос и таймеры не требуются. Любое действие всё равно повторно проверяет API.

Контрольная точка: UI соответствует матрице, а прямые `/admin` и `/metrics` под member показывают понятный отказ, сохраняя сеанс.

### 5. Подготовить запуск и демонстрационные данные

Добавить отдельный Compose с PostgreSQL и команды Make. Создавать admin из конфигурации и manager/member через seed. Повторный seed не сбрасывает пароль; неожиданная роль или неактивность демонстрационного аккаунта приводят к явной ошибке.

Контрольная точка: последовательность команд из README запускает приложение; все три аккаунта доступны; тестовая база отделена от демонстрационной.

## Примеры реализации

Это фрагменты выбранного подхода, а не альтернативная спецификация. Полный код хранится в перечисленных файлах.

### Политика и зависимость API

```python
class Role(StrEnum):
    ADMIN = "admin"
    MANAGER = "manager"
    MEMBER = "member"

ROLE_PERMISSIONS = {
    Role.ADMIN: frozenset(Permission),
    Role.MANAGER: frozenset({Permission.USERS_READ, Permission.METRICS_READ}),
    Role.MEMBER: frozenset(),
}

def require_permission(permission: Permission) -> Callable[..., User]:
    def check(current_user: CurrentUser) -> User:
        if permission not in ROLE_PERMISSIONS[current_user.role]:
            raise HTTPException(status_code=403, detail="Access denied: insufficient permissions")
        return current_user
    return check

@router.get("/", dependencies=[Depends(require_user_listing)], response_model=UsersPublic)
def read_users(session: SessionDep, skip: int = 0, limit: int = 100):
    ...
```

`CurrentUser` получает пользователя из БД, а не доверяет присланной роли. Проверка владельца конкретного объекта остаётся в обработчике ресурса.

### Разделение собственного профиля и административных полей

```python
class UserUpdateMe(SQLModel):
    model_config = SQLModelConfig(extra="forbid")
    full_name: str | None = Field(default=None, max_length=255)
    email: EmailStr | None = Field(default=None, max_length=255)
```

Запрос `PATCH /api/v1/users/me` с `{"role": "admin"}` должен вернуть 422. Повышение роли через `/users/{id}` требует административного разрешения.

### Перенос старых записей

```python
op.add_column("user", sa.Column("role", sa.String(16), nullable=False, server_default="member"))
op.execute("UPDATE \"user\" SET role = 'admin' WHERE is_superuser = true")
op.create_check_constraint("user_role_check", "user", "role IN ('admin', 'manager', 'member')")
op.drop_column("user", "is_superuser")
op.alter_column("user", "role", server_default=None)
```

### Проверка capability в интерфейсе

```tsx
export function can(
  user: UserPublic | null | undefined,
  permission: UserPublic["permissions"][number],
) {
  return user?.permissions.includes(permission) === true
}

// Разрешения получены от /users/me.
if (!can(user, "users:read")) return <AccessDenied />

// Административное действие скрыто для менеджера.
{can(user, "users:write") && <AddUser />}
```

### Проверка отзыва прав без нового токена

```python
assert client.get(f"{API}/metrics/", headers=manager_headers).status_code == 200
assert client.patch(
    f"{API}/users/{manager.id}",
    headers=admin_headers,
    json={"role": "member"},
).status_code == 200
assert client.get(f"{API}/metrics/", headers=manager_headers).status_code == 403
```

## Порядок проверки

1. **Проверить состав.** Сверить исходный SHA, лицензию и изменённые файлы. Убедиться, что исходники не потерялись из-за локального глобального `.gitignore`, а `.env`, JWT и браузерные auth-файлы не попадают в Git.
2. **Запустить приложение.** Из `fullstack/`: скопировать примеры `.env`, выполнить `make install`, `make db`, `make migrate`, `make seed`; в двух терминалах — `make backend`, `make frontend`. Открыть `http://127.0.0.1:5174` и проверить API health.
3. **Проверить миграцию отдельно.** На одноразовой базе применить исходные миграции до `fe56fa70289e`, вставить старого admin и обычного пользователя, обновить до head. Проверить роли и запрет недопустимого значения. Выполнить downgrade и повторный upgrade; не использовать демонстрационную базу.
4. **Запустить backend-тесты.** Создать отдельную `evios_test`, выполнить команду ниже. Проверить разрешённые и запрещённые пути для всех ролей, неизменность данных после запрета и отзыв прав с тем же JWT.
5. **Проверить удалённый endpoint.** Проверить 404 и отсутствие `Location` у `/api/v1/private/users/` в режиме разработки и с собранным frontend. Это не должен быть HTML приложения или 405 от статического обработчика.
6. **Запустить статические проверки и сборку.** `make check`; `make client` не должен оставлять неожиданные расхождения с закоммиченным клиентом. При изменении модели/API клиент генерируется повторно; при добавлении маршрута обновляется дерево TanStack.
7. **Запустить существующие браузерные admin-тесты.** Проверить создание пользователя, назначение роли, изменение, удаление и отказ участнику. Не считать один лишь успешный build доказательством работающего UI.
8. **Пройти ручную матрицу в браузере.** Admin: Users и действия; manager: Users без изменения и Metrics; member: отсутствие этих пунктов, Access denied при прямом открытии обоих URL, доступ к Settings. Переключить аккаунты в одном сеансе браузера и убедиться в отсутствии чужого cache. Проверить отказ на ширине 390 px.
9. **Подготовить сдачу.** Сохранить скриншоты и проверенные результаты в `docs/verification.md`, экспортировать диалог до указанного времени, проверить diff и секреты, создать завершающий коммит и push. Проверить PRIVATE и совпадение локального/удалённого SHA.

## Принятые решения и риски

Выбрана небольшая политика на FastAPI-зависимостях: её достаточно для трёх фиксированных ролей, и она проверяется вместе с настоящими маршрутами. Полноценный движок политик увеличил бы объём и сложность без требования работодателя.

Список capability передаётся backend, чтобы UI не поддерживал отдельную копию матрицы. Роль/активность читаются из БД для немедленного отзыва API-доступа. UI может показывать уже загруженное состояние до обновления query или навигации; это не даёт права выполнить запрещённый запрос. Постоянное обновление интерфейса без действия пользователя не входит в объём.

Путь `/admin` сохраняется как существующий путь списка пользователей, доступный также менеджеру. Это расширение прав чтения существующего раздела, а не alias удалённого маршрута. Список ограничен первыми 100 пользователями по поведению шаблона; полноценная пагинация не добавляется.

Downgrade теряет отдельную роль manager. Пример конфигурации предназначен для локальной проверки; продакшен-развёртывание приложения не является результатом первого задания. Email-зависимые функции и весь остальной frontend шаблона не следует считать проверенными только по целевому admin-набору.
